# AGENTS.md：记录影响下一次改动的仓库约定

找出自动化助手最容易做错、而项目又已有答案的事情。例如，哪些文件由生成器维护，改接口定义后要从哪个目录重新生成，哪组测试覆盖旧格式。每条约定写清触发条件、动作和验证方法。构建脚本或 CI 已封装步骤时，引用入口即可。

## 作用范围

共用约定放在仓库根部。某个包确有独立工具链、测试夹具或架构边界时，才在该子目录补充差异。Codex 从项目根目录向启动时的工作目录逐层装载指令，较近的指令可以覆盖上层指令。同一层若有非空的 `AGENTS.override.md`，优先读取它。若从根目录启动而工作涉及更深的包，另行查看目标路径上的局部指令。[OpenAI Docs 的 AGENTS.md 指南](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 把约定写到可以照做

- **命令**　从项目脚本、贡献指南或 CI 找到真实入口，写明工作目录、前置条件和适用改动。分清一个测试的快速反馈与合并前的完整检查。Apache Airflow 的仓库指令按开发环境和检查范围组织命令。[Apache Airflow 的 AGENTS.md](https://github.com/apache/airflow/blob/main/AGENTS.md)
- **边界**　说出哪条路径是事实来源、哪里是生成物。比如一个项目从接口定义生成客户端，就记录接口定义的位置和项目自己的生成命令。用仓库中已有的约定支撑规则，避免把个人推测写成项目政策。
- **导航**　读详细说明前给出触发条件，例如“修改存储格式时，读取兼容性规格”。首次安装和产品示例链接 README，完整契约链接规格。把只跟本次任务有关的临时要求留在任务里。[AGENTS.md 开放格式](https://agents.md/)

从指令声称适用的目录核对命令，确认指向的脚本、测试和文档都存在。若命令会发布版本、部署或改变共享数据，用脚本定义核对其用途，按当前任务的授权范围选择本地验证。
