# 从需求到可复查的变更

先弄清谁在做什么、目前发生了什么、怎样观察到改动成功。对已有项目，用入口、测试和适用的仓库指令核对现状。空仓库先从用户给出的场景确定最小可交付结果。小修复可以直接用复现步骤和断言记录目标。修改公共契约、持久化数据格式或多模块交互时，用一份简短规格保存约定。

1. **明确验收。** 把一个用户可见结果对应到一项检查。若还存在几种会产生不同结果的解释，先核对已有承诺，再澄清真正影响实现的分歧。修复故障时尽量在改动前复现并记录现象。
2. **实施一个可独立验证的改动。** 沿用仓库的实现入口与测试设施。按验收例实现行为，让相关代码、测试和必要的文档能一起审查。涉及迁移时，考虑已有数据在失败、重试期间的状态，以及如何恢复或回退。[Google 的小型变更指南](https://google.github.io/eng-practices/review/developer/small-cls.html)
3. **从正常入口验证。** 先运行能发现该问题的最小检查，再按照改动影响和仓库要求扩展到集成、兼容性或构建检查。若声称改善性能，在相同负载和条件下比较前后数值，同时记下代价。[Linux 内核补丁指南](https://docs.kernel.org/process/submitting-patches.html)
4. **复查差异。** 以调用者身份核对验收例，再以维护者身份检查失败路径、过度复杂的实现和测试盲点。用户操作变了就更新 README，承诺变了就更新规格，仓库工作方式变了就更新 AGENTS.md。[Google 的代码审查指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

审阅已有项目时，可把每项偏差记为“文档承诺 → 实际行为及位置 → 用户影响 → 建议修正”。例如，README 声称默认输出 JSON，而命令实际输出纯文本，先查发布版本的约定和回归测试，再判断是示例过期还是实现回归。交付时列出实际执行的检查、观察到的结果和仍缺少的验证条件。
