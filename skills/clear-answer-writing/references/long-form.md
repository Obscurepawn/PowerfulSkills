# 长文写作规则

适用于新写或改写约 1500 字以上的文章、技术博客、文档、报告和教程。短输出只用 SKILL.md。

长文的 AI 痕迹主要不在单个词，而在剂量和结构：限定句逐段出现，标题密而整齐，每节都是“结论标题 → 解释 → 限定 → 收尾句”，全文看不出作者。下面的规则针对这些问题。

## 1. 动笔前先定三件事

1. **读者和他已经知道什么。** 写给已经熟悉 Linux 的工程师，就不要每处都解释“不能据此推出”。
2. **全文最重要的 3–5 个坑。** 这些是你要花篇幅写透、写狠的地方。其余提醒都降级：一句带过、合并，或者删掉。
3. **作者手里有什么一手材料：** 实测数据、命令输出、排障经历、踩过的坑。有就用第一人称写进去；没有就老实不写，也不要用“假设/示例”反复提醒读者自己没做过。

## 2. 结构

- **标题密度：** 平均每 600–1200 字一个标题（含二级、三级）。一节只有一两段时，并到相邻小节。
- **标题写对象或问题，不写结论。** 结论放在正文里，读者读到时才有分量。

| 结论式（避免） | 对象或问题式（推荐） |
|---|---|
| 从一条行情到一笔订单，先标清测量边界 | H0、C0、C4、H1 |
| 多台交换机不必然带来逐跳时钟比较 | 中间隔了五台交换机，要比几只钟？ |
| 硬件时间戳无法自动消除路径不对称 | 路径不对称 |
| 最终报告应给出怎样的结论 | 报告怎么写 |

- **标题句式不要重复。** 同一个起首字（“先……”“如何……”）最多出现三次。
- **小节功能要有变化。** 有的节只讲一个例子，有的节只给一张表或一段命令，有的节直接推进判断。不要每节都按“概念 → 解释 → 限定 → 总结”铺开。
- **详略要有落差。** 重点的坑写三五段，次要概念一两句带过。段落长短过于均匀，本身就是一个信号。

## 3. 限定和免责的剂量

| 类型 | 剂量 | 做法 |
|---|---|---|
| 否定式提醒（“不能/不代表/不等于/未必”） | 每千字约 1 处以内 | 只留会导致算错、配错或决策错误的地方 |
| 模糊情态（“可能/通常”） | 每千字约 1–2 处 | 写出条件；有依据就直接判断 |
| 指令口吻（“应/需要/必须”） | 每千字约 3 处以内 | 一部分改成“否则会……” |
| “示例/假设/未实测”声明 | 全文 1 次 | 放在文首或第一次出现时 |
| 段尾限定句 | 长段落的 20% 以内 | 段落停在事实、结论或后果上 |

**改前（每段都在设防）：**

>

## 4. 开头、过渡和结尾

- **开头：** 直接进入问题或场景，不写“本文将从 A 讲到 B 再到 C”。确实需要阅读地图时，用一句话交代，不要列目录。
- **过渡：** 删掉“前面已经能解释……接下来需要回答……”“回到开头的例子”这类句子。章节标题本身就是过渡。
- **节尾：** 删掉复述句，例如“跨时钟域取决于参与计算的读数来源，不取决于报文穿过了多少设备”。要么停在上一段的事实上，要么换成一个具体的坑或可以照做的建议。
- **全文结尾：** 停在最后一个有用的内容上（一份检查清单、一个可执行建议），不再升华一句“这样才能……”。

**改前：**

> glibc 是应用接口层，vDSO 是一条实现路径，内核 timekeeping 管理时间状态，硬件计数器提供计数来源。把它们分清之后，就不会把“vDSO”和“TSC”当成两个完全独立的时间来源。

**改后：**

> 拿“vDSO 和 TSC 哪个快”做对比时要小心：在 TSC 当 clocksource 的机器上，vDSO 快速路径读的本来就是 TSC，差别只在多了一次换算和一次序列号检查。

## 5. “要分清”和抽象名词

“这里要分开两种能力”“这是两个问题”“还有三个独立问题”这类句子是在预告区分，而不是直接区分。直接写出差别：

> 改前：这里要分开两种能力：参与 PTP 同步，以及把普通业务报文的时间戳导出给观测系统。支持前者，不自动代表具备后者。
>
> 改后：交换机支持 PTP，只说明它能帮你对时；能不能导出业务包的逐跳时间戳，是另一项要单独确认的功能。

抽象名词要落到具体对象上：“时间关系失效”写成“PTP 失锁”或“phc2sys 退出”；“具有不同的挂起语义”写成“会把系统挂起的时间算进去”。

## 6. 作者在场

- 技术长文不需要口语化，但要让人看出背后是一个做过这件事的人。
- 有实测就给真实数字和命令输出，哪怕只有一组。一个真实数字，比十句“这是示例”更可信。
- 有排障经历就在对应位置写两三句第一人称。没有就不写，**不编**。
- 标题口吻和正文口吻要一致。标题玩笑轻松，正文却像国标规范，读起来会很割裂。

## 7. 收尾检查

1. 运行 `scripts/ai_style_check.py`，逐项处理超阈值项。
2. 改完再跑一次，确认指标下降，同时没有误删事实、条件和必要限定。
3. 通读一遍，问自己：删掉这句，读者会不会少知道什么、或者更容易出错？不会，就删。
4. 脚本数值全部过关不代表写好了。阈值只覆盖能计数的模式，最终以通读为准。
